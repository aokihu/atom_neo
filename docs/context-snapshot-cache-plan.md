# Context Snapshot 缓存优化实施方案

## 状态与基线

- 分支：`codex/context-snapshot-cache`。
- 基线提交：`485b36426cb6f7a7fd76907607cc060a78b08d68`。
- 当前阶段：用户已记录基线；混合格式、步骤刷新与缓存统计已实现，本地及六次真实小样本验证完成。
- 工作区已有 TUI、相关文档及 sandbox/config.json 修改，不属于本次优化，不覆盖、不提交。
- HTML/Web 文档不再维护；Markdown 为唯一维护入口。
- 本地测试不调用真实 LLM，字符长度和共同前缀不能换算成实际费用。真实 Token 消费由用户对比。

## 目标与边界

静态指令使用普通文本，动态数据使用 TOON。稳定指版本有效期间不变，不等于 pinned 或某个 scope。
保留 ContextService 的所有权、Scope、预算选择、Snapshot `{ id, content }`、Receipt 和 lease。
不扩展消息窗口、不引入额外摘要 LLM、不建立新的缓存服务。模型消息及工具定义仍独立传递。

## 输出合同

1. Entry/Fragment 增加可选 `format: "text" | "toon"`，默认 toon；旧持久化数据仍可读取。
2. text 只允许显式 trusted、instructions channel、字符串内容，非法组合在服务与编译边界拒绝。
3. 系统提示、AGENTS、平台指令、激活 Skill 用 text；正文先净化 Unicode，保留原文路径与转义。
4. 文本指令在前，动态 TOON 在后。禁止把动态条目数量、时间、版本或 Snapshot ID 放在静态前缀。
5. 动态条目独立编码，保留 trust/scope/channel/source；对象保持嵌套结构，不先编码成字符串再编码。
6. 动态区固定类别顺序：环境、Memory、累计摘要、工具摘要/归档索引、任务状态/时间、临时指导。
   未知来源采用确定性兜底顺序。文本区按系统、工作区/平台、Skill 排列。
7. 预算优先级只负责选择；显示顺序不受动态条目的高优先级影响。
8. 分块标记和输出解析测试应在实现阶段统一；测试先行阶段只断言正文前缀、信任约束等外部合同，
   不锁定尚未实现的标点或标题。

## 实施顺序

### 1. 测试与用户基线（已完成）

先运行已有 compiler/service 测试记录基线，再运行新增 cache 测试，确认预期失败来自未实现的合同。
新增用例覆盖动态增删、更新和预算淘汰不破坏静态前缀，纯文本输出，格式信任约束，确定性与转义。
不使用 skip/todo 隐藏预期失败；生产代码实施后这些测试必须全部通过。

2026-09-14 本地结果：

- `bun test src/packages/core/src/context/compiler.test.ts src/packages/core/src/context/context-service.test.ts`：24 pass / 0 fail。
- `bun test src/packages/core/src/context/compiler-cache.test.ts`：3 pass / 8 fail（11 个新用例）。
- 预期失败对应原始文本输出、动态增删/淘汰的静态前缀、Skill 排列、text 信任/类型约束和普通文本转义。
- 已通过确定性、内部 ID 不泄漏和 Receipt 预算选择。没有请求真实模型，也没有费用测量结果。
- 当前直接运行完整测试会包含这 8 个预期失败；这是生产实现前的测试先行状态，不是已完成优化。

### 2. 混合格式

修改 shared context 类型、ContextService 格式校验/传播、compiler 输出；保持去重、预算及 Receipt 行为。
修改 record-context 的生产条目，拆分 task-environment：固定执行规则与结构化 environment/task-state。
TODO 保留 content/status/priority，去掉装饰图标和重复规则。Memory 保持 untrusted。
时间每轮采样一次；精确 Token 用量是否撤出提示，先检查实际依赖。
Skill 排列确定化，加载/卸载仍在下一模型步骤生效。同步修改旧的全量 TOON 解码测试。

### 3. 步骤与观测

统一初始及步骤快照预算，复用现有 Receipt/lease 管理实际使用的快照。
无相关变化时复用正文；必要状态变更时更新相应数据，不重复采样时钟。
增加逐步骤 inputTokens/cacheReadTokens/noCacheTokens/outputTokens，缺失值为未知。
静态 hash、工具定义 hash、长度、重建原因只记录日志，不注入模型。
补充服务格式传播/持久化、动态结构 round-trip、步骤预算、成功消费/失败重试及 usage 缺失测试。
随后运行相关测试、类型检查及项目要求的完整检查。

## 用户 Token 对比流程

测试前和修改后开始真实验证前均告知用户；不自动启动真实 LLM 或声称测得费用。
用户先在现有生产实现记录优化前数据，再在实现完成版本使用同一 provider/baseURL/model、
工具集合、参数和可比 Session/Memory 初始状态运行相同场景。记录工作区配置，避免混入 TUI 改动差异。

| 场景 | 对比点 |
|---|---|
| 相同工作区连续普通对话 | 静态前缀复用与跨轮动态更新 |
| 多步骤工具任务 | 逐步追加消息与累计输入量 |
| 加载/卸载 Skill | 系统与工作区前缀是否保留 |
| 注入 Memory、更新 TODO | 动态新增/更新的影响 |
| 一次性建议、压缩恢复 | 消费和摘要更新是否正确 |

每组分别记录首次请求与预热后的多次请求；缓存落盘和清理会影响结果，不能把第二次未命中当失败。
汇总命中率为 `sum(cacheReadTokens) / sum(inputTokens)`，同时比较未缓存输入、输出、调用次数及任务完成质量。
费用使用用户实际供应商价格计算，不硬编码单价，不以字符数/4或 hash 推断命中量。
收益验收以同类任务总费用下降且任务质量不退化为准，不设置无实测依据的百分比承诺。

## 已知限制

动态 TOON 仍在消息历史前面，跨轮动态更新仍会截断后续历史的缓存前缀。
第一版优先保障稳定指令及同轮工具循环；是否移动动态数据到历史末尾，由实际 Token 对比再决定。
本地 tests 不证明供应商缓存命中，也不模拟收费。
